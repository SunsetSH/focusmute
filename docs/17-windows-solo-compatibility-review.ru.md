# Краткое ревью: FocusMute, Windows и Scarlett Solo 4th Gen

Дата: 21 сентября 2026. Версия исходников и запущенного приложения: 0.11.0.

**Вывод:** основная обнаруженная проблема — неполная поддержка протокола Solo в FocusMute. Соединение с официальным Windows-драйвером работает, но LED-команды используют адреса Scarlett 2i2. Заявление README об автоматической поддержке Solo шире фактических возможностей реализации. План исправлений: [18-solo-mute-technical-plan.ru.md](18-solo-mute-technical-plan.ru.md).

## Основания и пределы проверки

Изучены библиотека, Windows/WASAPI backend, tray/CLI, настройки, reconnect, blink, тесты и исследования протокола в `docs`. Дополнительно прочитаны локальные `%APPDATA%\Focusmute\focusmute.log`, `schema_cache.json`, сведения установленного ПО и **живая firmware schema подключённого Solo через PAL/SwRoot**. Использованы штатная последовательность открытия сессии и команды чтения INFO_DEVMAP/GET_DEVMAP; SET_DESCR, DATA_NOTIFY и переключения mute/Air/Direct при исследовании не выполнялись.

Установленные компоненты: Solo firmware **2.0.2417.0**, файл `FocusriteUsbSwRoot.sys` **4.150.0.432**, Focusrite Control 2 **1.1139.0.0**. В реестре ОС: DisplayVersion **25H2**, build **26200.9457**. Это данные текущего окружения, а не заявление о проверке всех этих сочетаний версий. Воспроизводящий эксперимент с визуальным наблюдением Air ещё не проведён.

## Наиболее существенные находки

| Приоритет | Проблема | Доказательство и следствие |
|---|---|---|
| P0 | Запись LED-цвета в неверные поля Solo | `led/ops.rs::set_single_led` пишет 4 байта в 84 и 1 байт в 88. Живая схема Solo: цвет — 80, индекс — 84, массив цветов — 88. Запись цвета затрагивает также `factoryTestMode`/`factoryTestSwitchesBitmap`. Нельзя считать успешный IOCTL подтверждением правильного действия. |
| P0 | Прогноз LED-карты принимается за подтверждённую карту | Профиль есть только для 2i2. `layout.rs` назначает номера входов 0 и 8 по формуле и помечает их `High`; схема Solo сообщает размеры массивов, но не физическое назначение каждого LED. Ошибочный адрес и ошибочный физический индекс — разные риски. |
| P1 | Восстановление номера входа использует чужую семантику | `restore_number_leds` читает `selectedInput` по адресу 331. У Solo этого поля нет: байт 331 относится к `appCallbackMaxCycles`. Нативный цвет номеров Solo связан с Combine Inputs, а не с Select. |
| P1 | Выбор USB-устройства и микрофона Windows независимы | `WasapiMonitor::new` берёт `eCapture/eConsole` при старте. Нет выбора endpoint ID, проверки соответствия Scarlett и `IMMNotificationClient` для смены устройства. Можно менять mute другого микрофона, показывая его на Solo. |
| P1 | Reconnect может использовать устаревшую модель | При существующем `ctx` `TrayState::try_reconnect` применяет прежнюю стратегию без повторного разрешения контекста. Это неверно после замены модели/прошивки и опасно для будущих сохранённых LED-состояний. |
| P2 | Неполное извлечение capabilities | `parse_schema` читает controls только первого physical input. У Solo там Inst, а Air/48V находятся у второго: они теряются при прогнозировании кнопок. |
| P2 | События устройства ещё не подключены к приложению | `wait_notify` реализован в Windows backend, но tray принимает только `MutePoll` и `BrowserMute`; физические кнопки в рабочий цикл не включены. |

Основные файлы: [ops.rs](../crates/focusmute-lib/src/led/ops.rs), [protocol.rs](../crates/focusmute-lib/src/protocol.rs), [schema.rs](../crates/focusmute-lib/src/schema.rs), [layout.rs](../crates/focusmute-lib/src/layout.rs), [audio.rs](../crates/focusmute-lib/src/audio.rs), [tray/state/mod.rs](../crates/focusmute/src/tray/state/mod.rs).

## Почему полоска уровня продолжает работать при mute

Это **текущее намеренное поведение исходников**: `MuteStrategy` выбирает только светящиеся номера входов; `apply_mute_indicator` не меняет ни halo-сегменты, ни палитру `LEDcolors`, ни режим metering. README описывает именно это. Поэтому ожидание сплошного выбранного цвета на индикаторе уровня требует новой стратегии отображения, помимо исправления Solo-адресов.

Mute реализован через Windows endpoint volume, а аппаратный измеритель видит сигнал на входе интерфейса. Такая индикация сама по себе не доказывает, что собеседник слышит микрофон. `mute_inputs = "2"` выбирает LED-индикацию второго входа, а не отдельное заглушение одного канала стереопары. Программный endpoint mute нельзя считать универсальным аппаратным mute для ASIO, Direct Monitor и всех exclusive-mode сценариев; Microsoft отдельно описывает различие аппаратного и программного mute для WASAPI. [IAudioEndpointVolume](https://learn.microsoft.com/en-us/windows/win32/api/endpointvolume/nn-endpointvolume-iaudioendpointvolume).

## Почему исчезает Air

**Подтверждён дефект, способный нарушать индикацию на каждом mute/unmute:** обе операции вызывают `set_single_led` с адресами 2i2. На Solo четыре байта цвета попадают в индекс и соседние поля, настоящий цвет не записывается, а команда `DATA_NOTIFY(8)` выполняется с неправильными параметрами. Подробная побайтовая цепочка приведена в плане.

**Наиболее вероятное объяснение симптома:** ошибочная single-LED операция переопределяет индикацию; штатное переключение Air заново отрисовывает её. Но соответствие физического Air индексу, реально затронутому прошивкой, ещё не проверено. Нельзя объявлять доказанным ни «Air — LED 0», ни отключение самого Air DSP. Адрес `inputAir = 62` непосредственно этой функцией не записывается. Сначала нужны правильные адреса и карта LED, затем контроль Air Off/Presence/Presence & Drive до и после mute. Переключать Air туда-обратно как постоянный способ восстановления подсветки не следует: это меняет обработку звука.

## Совместимость физической кнопки Direct

Чтение состояния и уведомления технически доступны. Живая схема Solo: `directMonitoring` — **264**, `notify-device = 12`, `notify-client = 0x00800000`; у 2i2 используются другие значения. Однако это уведомление **об изменении состояния**, а не документированное событие press/release с идентификатором источника. Оно не гарантирует различение физического нажатия и изменения из FC2, а две быстрые смены состояния могут быть объединены.

По официальной инструкции Solo штатно переключает Direct **одним** нажатием. Двойное нажатие для Direct будет новым поведением FocusMute. При этом удержание Direct три секунды уже занято переключением Combine Input 1 and Input 2. Эти жесты необходимо сохранить либо явно учитывать в режиме переназначения. [Аппаратные функции Solo](https://userguides.focusrite.com/hc/en-gb/articles/17505454690706-Scarlett-Solo-Hardware-Features), [Combine Inputs](https://support.focusrite.com/hc/en-gb/articles/14653126009490-Scarlett-Solo-4th-Gen-one-or-two-input-app-compatibility).

Вариант «изменился Direct → переключить mute» осуществим как эксперимент. Вариант «одиночное — только mute, двойное — Direct» условно осуществим, но потребует проверки потока событий и компенсации штатного действия. До такой проверки нельзя обещать отсутствие краткого переключения мониторинга или надёжное распознавание двойного нажатия.

## Что действительно относится к Windows

Рабочий транспорт уже есть: официальный драйвер, PAL, IOCTL_INIT/TRANSACT, сессия, overlapped I/O. Переустановка USB-драйвера или замена его на WinUSB не устраняет обнаруженные ошибки адресов. Основные задачи на стороне Windows — корректная привязка capture endpoint, обработка смены устройства/сна и завершение фонового I/O.

Для новой подписки на кнопки особенно существенен `ioctl_async`: по таймауту он делает `CancelIoEx(handle, None)`, отменяя **все** запросы данного handle, включая будущий NOTIFY. У worker нет сохранённого `JoinHandle`, а handle принадлежит внешнему `WindowsDevice`. Это требует пересмотра владения и остановки перед добавлением постоянно ожидающего запроса.

Исследования в `docs/09`, `docs/13`, `docs/16` преимущественно относятся к 2i2 и местами содержат устаревшие обобщения. Например, фактическая схема этого Solo содержит **32 LED, 2 аналоговых входа, 14 metering segments и не содержит selectedInput**. Его микрофон — Input 2; штатное объединение каналов важно для приложений, принимающих только первый канал. Эти сведения подтверждены локальной схемой и [пояснением Focusrite](https://support.focusrite.com/hc/en-gb/articles/14653126009490-Scarlett-Solo-4th-Gen-one-or-two-input-app-compatibility).

**Рекомендуемый порядок:** сначала схема/границы записей/восстановление и проверка Air; затем отдельная halo-индикация; затем подписка на Direct и эксперимент с жестами. Клавиатура и физическая кнопка должны обращаться к одному контроллеру mute.

Проверка сборки `cargo build --offline --locked -p focusmute --bin focusmute-cli` остановилась на отсутствующей в локальном кэше зависимости `base64 0.23.1`. Тесты и аппаратный эксперимент с записями не запускались; выводы основаны на исходниках, живой схеме, локальном журнале и первичных источниках. Исходники приложения этим ревью не изменены.
