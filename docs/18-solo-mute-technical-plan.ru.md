# Технический план: Solo 4th Gen, mute-индикация, Air и физическая кнопка

Дата: 21 сентября 2026. База: FocusMute 0.11.0, Rust workspace `focusmute-lib` + `focusmute`. Краткое ревью: [17-windows-solo-compatibility-review.ru.md](17-windows-solo-compatibility-review.ru.md).

## 1. Цель и границы

Исправить управление Scarlett Solo 4th Gen на Windows, добавить выбранный цвет на аппаратные индикаторы входного уровня при mute, сохранить штатную индикацию Air и исследовать переключение mute физической кнопкой совместно с клавиатурой.

Под «полоской» в этом плане понимаются аппаратные Gain Halo/индикаторы уровня входов Scarlett. Основной новый режим — **постоянный цвет при mute независимо от громкости**. Перекраска реагирующего на звук измерителя рассматривается как отдельный, более ограниченный вариант, а не как эквивалент постоянного цвета.

Этот документ — план реализации. Исправления исходников и эксперименты с изменением настроек устройства в рамках исследования не выполнялись. Поддержку всех моделей Scarlett и аппаратное заглушение всех аудиотрактов задача не предполагает.

## 2. Существующая архитектура и места расширения

| Слой | Текущая реализация | Необходимое развитие |
|---|---|---|
| Транспорт | `device.rs`, trait `ScarlettDevice`: descriptor read/write, TRANSACT, `wait_notify`; Windows PAL/SwRoot + I/O worker | Владелец сессии, сериализация составных операций, безопасное завершение worker/NOTIFY |
| Описание модели | `schema.rs`, `offsets.rs`, `models.rs`, `context.rs`, `layout.rs` | Полные типизированные поля и события из схемы; подтверждённая карта Solo; capabilities с происхождением |
| Mute Windows | `audio.rs::WasapiMonitor`, `IAudioEndpointVolume::SetMute`, callback с cached boolean | Выбор endpoint, повторное подключение audio backend, подтверждение команд и источник изменения |
| Логика индикации | `monitor.rs::MuteIndicator`, двухотсчётный debounce, `led/strategy.rs`, `led/ops.rs` | Разделить состояние mute и состояние применения LED; добавить halo-стратегию и восстановление |
| Приложение | `tray/shared.rs`, `tray/state/mod.rs`; сообщения `MutePoll`, `BrowserMute` | Единый контроллер запросов клавиатуры/меню/браузера/устройства и новые device events |
| Анимация | `tray/blink.rs`, GET_METER примерно раз в 90 мс, LED Off/Solid | Использовать тот же LED-session, не обходить capabilities прямым `set_single_led` |
| Интерфейс и CLI | `config.rs`, `settings_dialog/ui.rs`, `cli/{monitor,status,probe,map}.rs` | Выбор режима индикации/кнопки/endpoint, диагностика, одинаковые правила восстановления |

Основной поток сейчас:

```text
Hotkey / tray / browser -> WasapiMonitor.set_muted()
WASAPI callback -> poll thread -> Msg::MutePoll
  -> MuteIndicator (debounce) -> apply/clear LED -> ScarlettDevice
```

`DeviceContext` вычисляет `offsets`, но основной `set_single_led` их вообще не получает. Поэтому расширить только `DeviceOffsets` недостаточно: правильное описание полей должно пройти через весь путь strategy → indicator → LED operations, включая blink, reconnect, settings apply и CLI.

## 3. Проверенные данные именно подключённого Solo

### 3.1. Метод проверки

В локальном журнале: FocusMute 0.11.0, Scarlett Solo 4th Gen, firmware 2.0.2417.0, предупреждение `using predicted LED layout (no hardcoded profile)`. Локальный кэш сообщает 32 LED и отсутствие `selectedInput`.

Затем выполнено чтение живой схемы через тот же PAL-интерфейс, что использует приложение: IOCTL_INIT → USB_INIT → GET_CONFIG → INFO_DEVMAP → GET_DEVMAP, распаковка zlib JSON. Временный Python/ctypes вызов имел allowlist команд чтения и инициализации; управляющие SET_DESCR/DATA_NOTIFY не отправлялись. Приведённые ниже Solo-адреса взяты из этой схемы, а не вычислены сдвигом относительно 2i2.

| Поле | Solo: адрес, размер | Solo notify-device | Значение/использование в существующем коде 2i2 |
|---|---|---|---|
| `enableDirectLEDMode` | 72, u8 | отсутствует у самого поля | 77 |
| `directLEDChannel` | 73, u8[2] | — | Не используется обычной индикацией |
| `directLEDDevice` | 75, u8 | — | Не используется обычной индикацией |
| `directLEDColour` | 80, u32 | 8 | 84 |
| `directLEDIndex` | 84, u8 | 8 | 88 |
| `factoryTestMode` | 85, u8 | 7, parameter buffer | Не должен затрагиваться LED-записью |
| `factoryTestSwitchesBitmap` | 86, u8 | — | Возможный исследовательский read-only источник, не готовый API кнопок |
| `directLEDValues` | 88, u32[32], 128 байт | 5 | 92, u32[40] в default profile |
| `parameterValue` / `parameterChannel` | 216 / 217, по u8 | — | 252 / 253 |
| `inputAir` | 62, u8 | 11, parameter buffer | 15 в исследованиях 2i2 |
| `meteringEnabled` | 263, u8 | 13, parameter buffer | Не используется текущим mute |

| `airPlusUsesAir` / `previouslySelectedAirMode` | 516 / 517, по u8 | 24 / — | Проверять состояние Air без принудительного переключения |

Enum Solo: LED modes Off=0, All=1, HalosOnly=2; Direct Off=0, Mono=1; Air Off=0, Air=1, AirPlus=2. `kNUMBER_METERING_SEGMENTS=14`, `kMAX_NUMBER_LEDS=32`, `kMAX_NUMBER_INPUTS=2`, `kPEAK_LENGTH=66`.

Push-маски Solo из `notify-client`: Air **0x00400000**, Direct **0x00800000**, Inst **0x01000000**, 48V **0x02000000**, Combine Inputs **0x04000000**. Это другой набор, чем в таблицах 2i2 из `docs/13`. `notify-device` — номер исходящей команды, `notify-client` — входящая битовая маска; смешивать их нельзя.

Схема содержит два аналоговых physical input: у Analogue 1 control `instrument`, у Analogue 2 — `air` и `phantom-power`. У controls этих входов `index = null`: нельзя автоматически подставлять физический номер 2 в scalar parameter buffer. Далее идут host USB inputs, которые не следует считать аналоговыми входами с halo.

### 3.2. Побайтовое доказательство ошибки mute/unmute

Текущая операция из `led/ops.rs`:

```text
SET_DESCR(84, color.to_le_bytes())
SET_DESCR(88, [предполагаемый LED index])
DATA_NOTIFY(8)
```

На Solo это означает:

1. Адрес 84 — **индекс**, а не цвет. Цвет `0xRRGGBB00` передаётся little-endian как `00 BB GG RR`: индекс становится 0 при любом таком цвете. Байты 85 и 86 затрагивают `factoryTestMode` и `factoryTestSwitchesBitmap`, байт 87 — промежуток перед массивом LED.
2. Адрес 88 — первый байт `directLEDValues[0]`, а не индекс. Для второго предполагаемого LED туда записывается 8.
3. Настоящий `directLEDColour` по адресу 80 остаётся прежним. Notify 8 существует и у Solo, поэтому запускает LED-операцию с ошибочными аргументами. При этом состояние фактического цвета и физическое назначение LED 0 здесь не измерены.

Эта цепочка одинакова для mute, unmute и восстановления на выходе. Например, красный `0xFF000000` пишет `00 00 00 FF`; восстановление белого `0x88FFFF00` пишет `00 FF FF 88`. Факт затрагивания поля factory test **не доказывает включение factory test**: для него схема предусматривает отдельный parameter-buffer/notify механизм.

`restore_number_leds` дополнительно читает байт счётчика производительности как `selectedInput`, затем выбирает цвета по ошибочной модели Select. На Solo номера штатно белые, а при Combine Inputs оба зелёные; это описано [Focusrite](https://support.focusrite.com/hc/en-gb/articles/14653126009490-Scarlett-Solo-4th-Gen-one-or-two-input-app-compatibility).

### 3.3. Степень уверенности по пользовательским симптомам

| Вопрос | Установлено | Ещё требуется |
|---|---|---|
| Полоска реагирует на звук | Исходники меняют только номера входов, не halo; плюс Solo LED-записи неверны | Проверить новую постоянную halo-индикацию на железе |
| Air гаснет после mute/unmute | На каждом переходе отправляется некорректная LED-операция; `inputAir` напрямую не меняется | Подтвердить физический индекс и сохранность Air DSP; проверить устранение симптома после адресного исправления |
| Mute с Direct | Есть состояние, параметры записи и уведомление Direct | Проверить push-доставку на данном Windows-драйвере и источник события |
| Разные single/double actions | Можно написать автомат жестов | Доказать наблюдаемость каждого нажатия и приемлемость компенсации штатного Direct |

## 4. Этап A — устранить ошибки совместимости и Air (P0)

### A1. Описание протокола из схемы

Расширить `schema.rs` и `offsets.rs` до типизированного описания поля: имя, offset, size, scalar/array, element size, notify-device, notify-client, parameter-buffer flag. Добавить `LedCapabilities`, `ControlCapabilities`, `NumberRestorePolicy`; не хранить параметры модели россыпью глобальных констант.

Обязательные данные для single LED: colour u32, index u8, notify, число LED. Для halo — mode enum, bulk array/notify либо документированная альтернативная операция, данные восстановления. Для Direct — scalar state, parameter buffer, notify и event mask. Отсутствующая capability отключает только соответствующую функцию; keyboard/WASAPI mute остаётся доступен.

Проверять точные размеры и границы полей, допустимый LED index, отсутствие записи поверх соседнего поля, согласованность массивов. Не делать fallback на 2i2 для неизвестной модели. Существующий 2i2 fallback допустим только как явно идентифицированный и проверенный профиль, с обозначенной областью firmware-совместимости. Не заменять обнаруженные Solo-поля набором ещё одних глобальных констант.

Исправить извлечение controls: читать каждый physical input, сохранять его тип, router-pin и ссылку на control; не брать только `physical-inputs[0]`. Поднять `SCHEMA_FORMAT_VERSION` и инвалидировать старый неполный кэш. Кэшировать по модели/прошивке/версии формата; для snapshot восстановления дополнительно привязываться к конкретному устройству и поколению соединения.

### A2. LED API и профиль Solo

Изменить `set_single_led` на операцию с валидированным device context/capabilities. Для исследованного Solo ожидаемая последовательность:

```text
SET_DESCR(80, ровно 4 байта цвета)
SET_DESCR(84, ровно 1 байт индекса)
DATA_NOTIFY(8)
```

Адреса в этом примере — диагностический эталон для прошивки 2.0.2417.0; в рабочем коде они приходят из схемы. Все три команды составляют одну сериализованную операцию. Внутренняя очередь не защищает от стороннего клиента FC2, поэтому совместную работу нужно проверить отдельно.

До подтверждения физической карты Solo не считать прогноз `0,8` разрешением на запись. Разделить `Predicted` и `Verified` независимо от численной правдоподобности. Обновить `layout.rs`: формула 8 LED на вход — гипотеза для неизвестных моделей, не доказательство назначения. Само наличие 32 LED и 14 metering segments не устанавливает порядок их индексов.

После адресного исправления провести управляемое картирование Solo: один индекс за шаг, минимально необходимая яркость, фотографическая/ручная фиксация Input 1, Input 2, сегментов, Air, Direct, USB; проверить влияние mode 0 и mode 2. Сначала доработать существующий `cli/map.rs`: сейчас он пишет mode в 77, который у Solo является `directMonitorAltOffset`, и подавляет ошибки `.ok()`. Текущую команду нельзя использовать как безопасную основу измерения Solo без исправлений. Результат — отдельный проверенный `ModelProfile` и fixture схемы с provenance; не генерировать «подтверждённый» профиль из одного прогноза.

### A3. Restore и проверка Air

Добавить политики восстановления:

- `SelectedInput` для подтверждённого 2i2: selected/unselected из текущего состояния.
- `VideoCallMode` для Solo: оба номера по текущему `videoCallModeEnabled`, с проверенными цветами/способом возврата firmware ownership.
- `Unsupported` для непроверенного устройства: не рисовать предположительный нормальный цвет.

При изменении Combine Inputs во время mute сохранять mute-индикацию; при unmute восстановить **актуальное**, а не стартовое состояние. Цвет LED нельзя достоверно восстановить чтением `directLEDValues`: исследование 2i2 показывает, что firmware-rendered цвета не обязаны отражаться в этом массиве.

Контроль Air: до перехода прочитать `inputAir`, `airPlusUsesAir`, `previouslySelectedAirMode`, Direct, Combine Inputs, sleep/mode; после перехода повторить. Испытать Off/Presence/Presence & Drive, сначала без FC2, затем с FC2. Отдельно записать видимую подсветку и состояние обработки, не подменяя одно другим. Не посылать toggle Air и не трогать 48V ради восстановления LED. Если после адресного исправления Air продолжит гаснуть, сравнить трассу точных LED-команд и проверить карту/renderer данной прошивки.

**Готовность A:** записи не пересекают границы полей; ни один путь mute/unmute/blink/exit не пишет в 85/86/77 на Solo; Air и прочие функции не меняются за 100 циклов mute/unmute. Нет чтения 331 как selectedInput на Solo. Проверен базовый 2i2 без регрессии.

## 5. Этап B — добавить выбранный цвет на halo (P1)

### B1. Явные варианты отображения

Ввести `IndicatorMode`:

| Режим | Поведение | Ограничения |
|---|---|---|
| `numbers` | Исправленное текущее поведение, меняются номера | Сохраняет совместимость старого config |
| `halos_solid` | Выбранные входные halo постоянно светятся mute-цветом даже при тишине | Основная цель запроса; требует подтверждённого захвата/восстановления halo |
| `halos_tinted` | Индикатор продолжает измерять звук, но использует mute-палитру | Только опционально; не выполняет требование постоянного цвета |

Старый TOML мигрировать в `numbers` без неожиданного изменения поведения. Для проверенного Solo предоставить выбор `halos_solid` в GUI и документировать как режим для данной задачи. Сохраняются `mute_color`, `mute_inputs`, `input_colors`. Если firmware может менять только общую палитру, не выдавать её за независимые per-input цвета.

### B2. Исследование механизма и критерий выбора

Начать с Solo `HalosOnly=2`, правильного mode offset=72 и проверенной карты. Исследовать, какие LED реально попадают под override и затрагивает ли `DATA_NOTIFY(5)` кнопки. В исследованиях 2i2 bulk notify в mode 0 имеет широкий эффект; одно название HalosOnly не гарантирует отсутствие побочных изменений на Solo.

Проверить последовательность «снимок управляемого состояния → подготовка цветов → вход в HalosOnly → применение выбранных halo → выход → восстановление». Если mode 2 захватывает все halo, а выбран только Input 2, обеспечить нормальную индикацию Input 1. Если этого нельзя достичь штатным firmware-rendering, на первом этапе явно ограничить `halos_solid` всеми входами либо признать per-input режим неподдержанным. Эмуляция измерителя по GET_METER — отдельная работа, не скрытый fallback.

Для `halos_tinted` схема уже даёт адрес палитры 288, 10 цветов и notify 17. Сначала сохранить 40 байт, изменить палитру, при unmute вернуть её. Не использовать 2i2 notify 9: у Solo это phantom power. Общая палитра может влиять на оба входа; поведение на нулевом уровне, clipping и на других индикаторах необходимо измерить.

Постоянно перезаписывать halo через notify 8 в mode 0 как способ борьбы с metering не следует: это может дать гонку, мерцание и лишний USB-трафик. Если стабильное владение halo без нарушения Air не подтверждено, оставить `numbers` и явно сообщать, что `halos_solid` пока недоступен.

### B3. Жизненный цикл индикации

В библиотеке выделить `LedSession`/`LedController` с состояниями Idle, Active, Restoring, Faulted. Состояние Windows mute и успешность LED-отрисовки учитывать отдельно: ошибка LED не должна размьютить микрофон или изображать неподтверждённый успех.

Снимок делать один раз перед первым override, а не при каждом blink. Хранить только затрагиваемые данные: mode/палитра/прочие реально изменяемые поля и provenance сессии. Не восстанавливать целиком APP_SPACE или сохранённые Air/Direct/48V поверх ручных изменений пользователя. При ошибке промежуточной команды выполнить ограниченное восстановление; при потерянном устройстве не проигрывать старые записи новому соединению.

Обработать startup в mute, hot reload цвета/входов/режима, blink, unmute, штатный exit, reconnect, firmware change. На reconnect заново разрешать capabilities до любых записей. `Drop` — дополнительная страховка, но не гарантия cleanup при crash/kill. Для постоянного override определить восстановление при следующем старте; не обещать автоматический cleanup после завершения процесса извне. При необходимости сохранять маленький журнал override с identity и проверкой схемы, а не общий дамп настроек.

`BlinkState` должен отдавать намерение отрисовки контроллеру; текущий прямой цикл `set_single_led(..., 0)` в `tray/shared.rs::apply_blink_action` удалить. Blink не должен освобождать ownership halo в off-фазе.

**Готовность B:** в тишине и при входном сигнале выбранный halo остаётся выбранного цвета; при unmute возвращается metering; Air/Direct/48V/USB остаются корректны. Режим `halos_tinted`, если реализован, подписан как отдельный. Проверены оба входа и индивидуальные цвета либо ограничения отражены в UI.

## 6. Этап C — mute с физической кнопки (исследование → реализация)

### C1. Штатное поведение и варианты

У Solo короткое нажатие Direct уже переключает мониторинг Off/Mono; удержание 3 секунды управляет Combine Inputs. Двойной клик не описан как штатная команда Direct. [Руководство Solo](https://userguides.focusrite.com/hc/en-gb/articles/17505454690706-Scarlett-Solo-Hardware-Features), [Combine Inputs](https://support.focusrite.com/hc/en-gb/articles/14653126009490-Scarlett-Solo-4th-Gen-one-or-two-input-app-compatibility).

| Вариант | Реализуемость | Побочный эффект |
|---|---|---|
| Direct state change → ToggleMute | Хороший первый прототип | Direct уже изменён прошивкой; FC2 может выглядеть как нажатие |
| Direct state change → SetMute по выбранному соответствию | Простой автомат состояния | Direct и mute связаны; нужен явный выбор соответствия |
| Single → только ToggleMute; Double → ToggleDirect | Условно, после проверки доставки событий | Нужны различение жестов, подавление эха и компенсация native Direct |
| Отдельная HID-кнопка/педаль → существующий hotkey | Запасной вариант, если Direct нельзя надёжно переназначить | Требует отдельного устройства, зато не меняет audio controls Scarlett |

Air и Inst тоже меняют аудиотракт; они не являются свободными HID-клавишами. 48V не рассматривать как обычный trigger mute. Назначения разрешать только по capabilities конкретной модели.

### C2. Пассивный диагностический listener

Добавить `device_events.rs` в библиотеку: проверка длины ответа, LE bitmask, модельные маски из схемы, typed events, monotonic timestamp и connection generation. Windows transport: IOCTL_NOTIFY **0x0022200C**, ожидаемый пакет **16 байт**, маска в **bytes 4..8** по существующему исследованию SwRoot. Это расположение проверить на текущей версии драйвера.

Обрабатывать маску как набор битов, а не проверку равенства. ACK/прочие события не считать нажатием. После Direct event читать scalar `directMonitoring` по адресу 264; обычный timeout подписки означает отсутствие события, а не disconnect. Нужны отдельные результаты `Event / Timeout / Cancelled / Disconnected / ProtocolError` вместо одного строкового TransactFailed.

Первый диагностический инструмент (`focusmute-cli events`, новая команда) только читает. Записывает время получения, raw mask, состояние Direct/Air/Combine, latency и поколение соединения; серийник маскируется. Сравнить одиночные/двойные/тройные/длинные нажатия, изменения FC2 и программные изменения. Проверить, приходят ли два события при возврате состояния в исходное, не объединяются ли они и существует ли различимый источник.

Можно отдельно исследовать чтение `factoryTestSwitchesBitmap` в **обычном режиме** как гипотезу доступности press/release. Включать factory test ради рабочего переназначения не планируется. Поле может быть неактивно или иметь другую семантику; его наличие в JSON не доказывает наличие пригодного button API.

### C3. Потоки и владение сессией

Не вызывать блокирующий `wait_notify` в Win32 message loop и не ставить его в очередь перед TRANSACT. Текущая реализация специально обходит worker, но постоянному listener нужен гарантированный lifetime handle.

Предпочтительно расширить транспорт до одного session owner: очередь составных управляющих операций и отдельный pending overlapped NOTIFY. Для helper thread использовать безопасный transport handle/RAII guard; не добавлять без обоснования `unsafe impl Sync for WindowsDevice` только ради `Arc`. Хранить join handles, отменять запросы по конкретному OVERLAPPED, дождаться завершения I/O, остановить и присоединить worker, затем закрыть handle. Устранить побочный эффект существующего `CancelIoEx(handle, None)` при TRANSACT timeout.

Не открывать вторую независимую управляющую сессию для каждого нажатия. Если выбран отдельный handle для NOTIFY, предварительно проверить требования драйвера к инициализации, привязке событий и сосуществованию с основным handle/FC2. Не переносить предположения Windows в Linux: Linux backend пока не переопределяет `wait_notify`; graceful unsupported обязателен.

### C4. Управление Direct с подтверждением

Схема Solo требует parameter buffer. Ожидаемая операция для scalar Direct:

```text
SET_DESCR(parameterChannel=217, [0])  # scalar index, НЕ код команды
SET_DESCR(parameterValue=216, [0 или 1])
DATA_NOTIFY(12)
GET_DESCR(264, 1)                   # подтверждение с ограниченным retry
```

Порядок index → value → activate соответствует `scarlett2_usb_set_config` в [Linux driver](https://github.com/torvalds/linux/blob/master/sound/usb/mixer_scarlett2.c). Реальные Windows-записи и задержку readback проверить отдельно. Устройство может применять команду асинхронно. Не использовать запись `[12]` в parameterChannel: часть старых исследовательских примеров проекта смешивает index и event ID.

Каждая собственная команда получает локальный transaction ID, ожидаемое значение, generation и deadline подтверждения. Событие, согласующееся с ней, обновляет состояние, но не создаёт новый жест. Это защита от эха, а не доказательство физического происхождения остальных событий. При неоднозначной гонке с FC2 остановить распознавание текущего жеста и resync, не угадывать ToggleMute.

### C5. Single/double click: автомат и ограничения

Достоверное выполнение требует потока **отдельных нажатий** либо доказанного эквивалента. Изменения конечного boolean по опросу недостаточно: два быстрых нажатия могут дать тот же boolean. Даже IOCTL_NOTIFY может объединить изменения, а время получения через USB не всегда равно времени физического нажатия.

Если проверка C2 подтверждает достаточную наблюдаемость, реализовать pure state machine с инъекцией `Instant`/виртуальных часов:

```text
Idle
  press -> PendingSingle(deadline = t + 350 ms, baseline_direct)
PendingSingle
  второй press до deadline -> Double; отменить single
  deadline                 -> Single
  long press / disconnect / ambiguous event -> Cancel + resync
Single -> ToggleMute
Double -> SetDirect(!baseline_direct); mute не менять
```

350 мс — начальная настройка, допустимый настраиваемый диапазон, например, 200–600 мс. Различить независимые single/double без задержки single нельзя: иначе при двойном нажатии mute уже успеет переключиться. Время ожидания должно быть видно в описании настройки. При наличии press/release считать короткий жест по подтверждённому отпусканию и длительности, чтобы 3-секундный hold не порождал single.

**Native Direct уже действует до приложения.** При одном нажатии прошивка меняет D на !D; чтобы одиночное действие стало только mute, приложение должно вернуть D. При двух нативных переключениях без компенсации состояние обычно возвращается к D, тогда двойной жест должен явно установить !D. При компенсации каждого переключения вести отдельное желаемое состояние — простое «два раза нажали, значит уже включено» неверно.

Сравнить два экспериментальных подхода: немедленная компенсация native toggle и компенсация после классификации. Первый сокращает слышимый интервал, но усложняет распознавание эха и второго клика; второй проще, но оставляет изменённый мониторинг на окно double click. Ни один не гарантирует нулевой слышимый импульс без возможности запретить штатную обработку на устройстве. Если такого механизма нет, продукт должен либо явно предлагать экспериментальный режим с этим ограничением, либо отказаться от эксклюзивного переназначения Direct.

Hold Combine Inputs: при press/release зарезервировать длительный жест; при одних state notifications событие Combine может прийти уже после ошибочно принятого single. В таком случае сохранение hold без лишнего mute не доказано — это критерий отказа от полного режима, а не повод надеяться на debounce. Triple click: после принятого double начать новый жест только после границы предыдущей пары; точное правило покрыть тестом.

**Решение go/no-go:** выпускать полноценный single/double только если испытания подтверждают доставку отдельных жестов, подавление собственного эха, отсутствие false mute при FC2 и сохранение hold. Иначе выпустить лишь явно ограниченный opt-in режим изменения состояния Direct, а точное переназначение оставить недоступным. Закрытие окна FC2 не доказывает исчезновение всех других управляющих клиентов.

## 7. Этап D — единое состояние mute и устойчивость Windows

Добавить `MuteController` в библиотеке: `Toggle`, `Set(bool)`, `PushToTalkPress/Release`, origin (`Keyboard`, `Tray`, `Hardware`, `Browser`, `ExternalOs`), sequence/generation. Keyboard, меню и Direct не должны независимо делать `!indicator.is_muted()`.

Сейчас indicator отстаёт от SetMute из-за callback/debounce; два быстрых toggles могут превратиться в две одинаковые команды. Это видно и в локальном журнале как повторяющиеся `toggle → muting` до подтверждения `muted`. Контроллер должен хранить подтверждённое и ожидаемое состояния, сериализовать намерения и сверяться с WASAPI после ошибок/таймаута. LED, звук, hooks, reverse browser sync обновлять один раз на подтверждённый переход. USB-event сам по себе не подтверждает Windows mute.

PTT интегрировать с тем же контроллером: при отпускании возвращать предыдущее состояние только если после начала PTT не было более новой явной команды keyboard/hardware/browser/OS. Не оставлять старый `ptt_active` способным отменить новое намерение пользователя. Изменение mute из Direct должно вызывать тот же звук и reverse sync, что keyboard; поведение suppression для browser сохранить.

Windows backend:

1. Поддержать explicit capture endpoint ID и режимы follow-default-console/follow-default-communications. По возможности сопоставить endpoint и USB device через PnP/container identity; friendly name не использовать как уникальный ключ. При неоднозначности дать выбор в UI.
2. Реализовать `IMMNotificationClient`: смена default, удаление/возврат endpoint и device state. Callback только ставит сообщение, пересоздание COM-объектов и регистрации выполняется на выбранном COM-потоке. API endpoint ID трактовать как opaque. [Microsoft](https://learn.microsoft.com/en-us/windows/win32/api/mmdeviceapi/nn-mmdeviceapi-immnotificationclient).
3. Отдельно восстанавливать audio session и USB session после unplug/sleep. Уведомления со старым generation игнорировать. Перечитывать фактический mute перед возобновлением отображения; не воспроизводить накопленные clicks после reconnect.
4. В `status --json` показывать USB model/firmware, capability provenance, endpoint ID/name/role, committed/pending mute, LED status, доступность кнопки и последнюю ошибку. Не представлять отсутствие audio monitor как подтверждённый live.

Область mute: выбранный Windows capture endpoint. Параметр `mute_inputs` остаётся визуальным. Проверить shared-mode запись отдельно от Direct Monitor и ASIO. Для exclusive WASAPI учитывать `QueryHardwareSupport`: software mute там может не действовать; не обещать универсальную тишину на всех путях. [Microsoft EndpointVolume](https://learn.microsoft.com/en-us/windows/win32/api/endpointvolume/nn-endpointvolume-iaudioendpointvolume).

Текущее автоматическое unmute при exit является отдельной существующей политикой. На этапе исправления адресов сохранить её поведение, но делать через единый контроллер и отдельно документировать; restore LED не должен сам становиться командой audio unmute. При будущем изменении политики предусмотреть отдельную настройку, без скрытой смены значения в этой доработке.

## 8. Конфигурация и совместимость интерфейса

Предлагаемые новые поля, **сейчас их в приложении нет**:

```toml
[indicator]
mode = "halos_solid"          # только после проверки capability Solo
mute_color = "#FF0000"
mute_inputs = "all"

[audio]
target = "endpoint"           # альтернативы: default_console/default_communications
endpoint_id = "<выбранный через GUI opaque ID>"

[hardware_button]
enabled = false               # opt-in после успешной аппаратной проверки
button = "direct"
gesture = "single_double"
single_action = "toggle_mute"
double_action = "toggle_direct"
double_click_ms = 350
```

Не принимать комбинацию `single_double` как поддержанную, если доступны только ненадёжные изменения состояния. Для простого режима использовать отдельное явное значение `gesture = "state_change"`; GUI сообщает, что Direct продолжает штатно переключаться. Настройки существующей клавиатуры сохраняются. Валидировать допустимые действия и диапазоны задержек; пересоздавать/останавливать listener при применении настроек.

Обновить GUI model (`FormSnapshot`, `ValidateParams`, build/validate), `Config::validate`, default/migration, status и README. Все ограничения объяснять пользовательскими словами; адреса/IOCTL оставить в диагностике. Изменение режима на неподдержанный не должно запускать неизвестные записи или падение tray.

## 9. Проверки, необходимые при реализации

### Автоматические проверки без устройства

- Реальные fixtures Solo 2.0.2417.0 и существующего 2i2: полный разбор полей, scalar null index, controls обоих входов, отсутствие selectedInput, размер/notify палитры, enum и маски событий; неверные типы/границы отключают capability.
- Memory-backed mock с байтовым APP_SPACE и журналом последовательности: write colour не меняет index/factory fields, write index не меняет массив; проверить не только словарь «какой offset записан», как в текущих mocks. Набор тестов должен воспроизводить старую ошибку Solo и падать на старом коде.
- Отдельно Air/Direct/48V/Combine invariants для apply/clear/blink/settings/reconnect/exit. Snapshot/restore не откатывает внешнее изменение controls.
- Ошибка после каждого шага составной LED-операции, короткий/ошибочный TRANSACT response, неуспешный firmware status при успешном DeviceIoControl. Сейчас write paths не проверяют содержимое ответа — включить эту проверку в транспорт.
- Gesture machine с виртуальным временем: границы окна, дубль/эхо, merged events, triple/hold, missing release, FC2 ambiguity, timeout, disconnect/generation. Обычный ACK и Combine event не переключают mute.
- MuteController: два быстрых toggle возвращают исходное состояние; keyboard + hardware; SetMute failure; задержанный callback; PTT + hardware; browser suppression/reverse sync; ровно один sound/hook на подтверждённое изменение.
- Shutdown I/O: pending NOTIFY и TRANSACT не используют закрытый handle, idle timeout не создаёт reconnect loop; один клиент управления на сессию.

После реализации: `cargo fmt --check`, `cargo clippy --workspace --all-targets -- -D warnings`, `cargo test --workspace`, Windows build CLI/tray. Linux build/test нужен для изменения общих traits/config и graceful unsupported кнопки. Эти команды — запланированные проверки, не результаты текущего ревью.

### Аппаратная матрица

| Область | Сценарии | Условие приёмки |
|---|---|---|
| Solo baseline | Текущая прошивка/драйвер; FC2 открыт и закрыт | Корректные команды, стабильный shared-mode mute и LED |
| Halo | Тишина, речь, пик; оба/один вход; разные цвета; blink | Solid не зависит от уровня; незатронутые LED работают штатно |
| Air | Off, Presence, Presence & Drive; 44.1/48/96 kHz; отдельно 176.4/192 kHz | Нет изменения выбранной обработки и потери подсветки; учитывать ограничение Drive выше 96 kHz из руководства |
| Direct | 100 singles, 100 doubles с разными интервалами, triples, удержания | Нет ложного mute; double не переключает mute; hold сохраняет Combine |
| Конкуренция | FC2 Direct/Air/Combine + keyboard/PTT/browser | Нет циклов эха, незапрошенных действий и потери новых намерений |
| Жизненный цикл | Старт muted, смена режима, exit, reconnect, sleep/wake, crash/restart | Нет применения старых snapshots к новой сессии; понятное состояние восстановления |
| Windows endpoint | Другой default mic, communications role, удаление и возврат endpoint | Управляется выбранный endpoint; UI не выдаёт чужой mute за mute Solo |
| Регрессия | 2i2, неизвестная модель, Linux unsupported events | Существующий рабочий режим сохранён; неизвестные capabilities не записываются |

Целевые задержки измерять, а не обещать заранее: подтверждённый keyboard mute→LED до 150 мс на исправном соединении; single при double-click режиме — окно 350 мс плюс транспорт/подтверждение. Текущий debounce в два отсчёта с 250-мс fallback может превышать первый ориентир, поэтому исследовать подтверждение собственных команд без лишнего debounce при сохранении фильтра внешнего дребезга. Зафиксировать p50/p95 и краткие изменения Direct в аудиозаписи; «не слышно на глаз» не является критерием отсутствия импульса.

## 10. Порядок небольших изменений и результаты

1. **Диагностические fixtures и schema/capabilities.** Зафиксировать полную обезличенную Solo-схему; добавить точные границы и regression tests. Уточнить ошибочные обобщения `protocol.rs` и docs.
2. **Адреса LED, проверка карты и восстановление Solo.** Провести этап A; обработать все вызовы, включая CLI map/blink. Это самостоятельное исправление пользовательской проблемы Air, не зависящее от кнопок.
3. **Владение LED и halo mode.** Выполнить B с аппаратным go/no-go; добавить GUI/config и recovery.
4. **Единый mute controller и endpoint lifecycle.** Выполнить D; подготовить устойчивую точку входа для физических событий.
5. **Device event transport + read-only CLI.** Выполнить C2/C3, собрать трассы текущего Solo/драйвера. Принять решение о доступных жестах до выпуска переназначения.
6. **Opt-in Direct и, при доказанной возможности, single/double.** Выполнить C4/C5, интеграционные тесты и аппаратную матрицу. Если строгий режим недостижим, явно зафиксировать конкретное ограничение и оставить доступным корректный ограниченный вариант.
7. **Документация и релизная проверка.** README должен отдельно описывать mute audio scope, LED modes, Solo support status и физические gestures. `docs/16` исправить: Solo имеет два входа, а default Windows endpoint не обязан быть Scarlett даже при единственном capture endpoint самого интерфейса.

## 11. Что проверено сейчас, что остаётся открытым

Подтверждены чтение устройства через официальный Windows-драйвер, живая карта полей/событий Solo, ошибочные записи существующего кода, отсутствие selectedInput и потеря controls второго входа. Установлено, почему текущая стратегия оставляет metering обычным.

Остаются аппаратные вопросы: физическая карта LED Solo, точный renderer-путь гашения Air, scope/restore HalosOnly, наблюдаемость отдельных нажатий и допустимость компенсации Direct. Они имеют явные эксперименты и критерии отказа в этапах A–C; обещать их решение исключительно правкой Rust-кода нельзя.

В текущем исследовании сборка `cargo build --offline --locked -p focusmute --bin focusmute-cli` остановилась из-за отсутствующего в локальном Cargo-кэше `base64 0.23.1`. Версии зависимостей не изменялись. Аппаратные write-тесты и unit tests не выполнялись; работоспособность предлагаемых изменений этим документом не заявляется.

Дополнительные первичные источники для последующей реализации: [официальные загрузки Solo/Windows](https://downloads.focusrite.com/focusrite/scarlett-4th-gen/scarlett-solo-4th-gen), [таблицы Solo и parameter-buffer в Linux driver](https://github.com/torvalds/linux/blob/master/sound/usb/mixer_scarlett2.c). Локальные выводы о конкретных LED-адресах основаны прежде всего на чтении подключённого устройства 21.09.2026, а не на переносе таблиц 2i2 из этих источников.
